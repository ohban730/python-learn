# Antigravity におけるファイル分析メカニズムとクラウド LLM アーキテクチャ

> **📄 概要**
> Antigravity エージェントがローカルファイルを分析・編集する際、裏側で RAG（検索拡張生成）を使っているのか、それともクラウド LLM の巨大コンテキスト処理を行っているのかのアーキテクチャ解説です。

---

## 💡 1. 結論：毎回 RAG を使っているわけではありません！

Antigravity でファイルやフォルダのパスを指定して分析を依頼された際、毎回 RAG（ベクトル検索）を挟んでいるわけではありません。

最新の **「クラウド LLM の超巨大コンテキストウィンドウ（Long Context Window）」** と **「エージェントツール (`view_file`) による直接読み込み」** の組み合わせによって実現されています。

---

## 🔄 2. ファイル分析の処理フロー

```text
 ［ ユーザーの指示 ］: 「c:\...\main.py を分析して」
         │
         ▼ 【 1. エージェントツールの実行 (view_file) 】
 ［ 指定されたローカルファイルを丸ごと読み込む ］
         │
         ▼ 【 2. クラウドの巨大 LLM へ直接投入 】
 ［ 超巨大コンテキストウィンドウ (100万〜200万トークン) ］
   ・ファイルの中身全体を「ノーカット」で一度にプロンプトへ注入！
         │
         ▼ 【 3. クラウドLLMの一括推論 】
 ［ コード全体の構造・依存関係・文脈を漏らさず分析して回答 ］
```

---

## 📊 3. 「RAG スタイル」と「巨大コンテキスト直接投入」の比較

| 比較項目 | RAG (検索拡張生成) スタイル | 巨大コンテキスト直接投入 (Antigravity) |
| :--- | :--- | :--- |
| **誕生背景** | コンテキスト上限が狭い（4k〜8k）モデルで長文を扱うための工夫 | 数十万〜数百万トークンを一括処理できる最新LLMの力技 |
| **データの渡し方** | 文章を短札状（数行）に刻んでベクトル検索し、ヒットした一部だけ渡す | **ファイル全体をノーカットで丸ごとプロンプトに注入** |
| **コード分析の精度** | 検索から漏れた離れた関数の定義や変数を見落とす（切断リスク） | **プロジェクト/ファイル全体の依存関係を 100% 漏らさず把握** |
| **主な用途** | 何万冊もの巨大ライブラリからの知識検索 | プログラミング、コードレビュー、リファクタリング |

---

## 🛠️ 4. どのような時に「検索」を行うのか？

Antigravity では、RAG ではなく **エージェントの「ツール利用 (Tool Use)」** という形で必要に応じて検索を行います。

1. **ファイルパスが分からない時**: `list_dir` でフォルダ構造を探索。
2. **特定キーワードの出現場所を探す時**: `grep_search` (ripgrep) でキーワードを高速全文検索。
3. **必要なファイルが特定できたら**: `view_file` でそのファイル全体を読み込んで一括分析。

---

## 📝 まとめ

* **RAG 依存からの脱却**: 最新のクラウド LLM（Gemini 等）は文庫本数十冊分のコードを一瞬で丸呑みできるため、RAG で細切れにしなくても高精度にコード全体を分析できます。
* **メリット**: コードの切り落とし事故が起きず、ファイル全体の流れや複雑な依存関係を正確に把握した上で回答・修正提案が可能になっています。
